# Realtime authorization

New OTP logins and refresh rotations issue an access token bound to that refresh token's unique session identifier. REST continues to accept an otherwise valid legacy access token until expiry. Socket handshakes require a bound token: legacy clients must refresh or log in and reconnect. Clients must reconnect with the replacement access token after rotation; the consumed refresh identifier invalidates the old connection's binding. Logout revokes only the supplied refresh token, preserving independent logins.

Each incoming action and each outgoing private delivery checks the access signature/expiry, current ACTIVE account, current role, and refresh-token revocation in the database. Booking chat additionally checks current parties and a messageable booking state; lifecycle booking notifications still reach parties in terminal states. Admin delivery requires the current ADMIN role. Checks run again before returning a private acknowledgment or emitting a packet. Account/session changes take effect on the next action or delivery; idle sockets disconnect at access expiry. This does not recall packets authorized before a concurrent change or already in flight.

REST and sockets share strict UUID, content-type, and message-length validation (1–4,000 characters). The shared message service also validates callers. Wire packets are limited to 16 KiB. Each user receives 120 actions per minute, including malformed actions, across reconnects and, with Redis, API replicas. Each socket permits at most eight pending actions and sixteen queued private deliveries. Redis-free development/tests use a bounded local user counter; production startup requires Redis. Errors expose stable codes and generic messages.

API nodes subscribe to application envelopes and authorize each local recipient. Workers publish through the same path. The namespace includes environment and Redis database because Redis Pub/Sub itself spans logical databases. Envelopes are limited to 64 KiB. The old direct Redis-to-socket broadcast path is no longer used. With Redis configured, an unavailable publisher/subscriber drops convenience signals; there is no local bypass or offline replay buffer. Receiving nodes still authorize packets already received. Clients recover authoritative state through the API. This remains best-effort delivery, not a durable notification outbox.

Roll out the API and worker transport together: the former Socket.IO Redis adapter/emitter protocol and the new authorized-envelope channel do not exchange broadcasts. Mixed versions can miss convenience signals. Validate cross-process delivery and reconnect clients with bound access tokens as part of deployment acceptance; API reads remain the source of recovery.

Closing the HTTP server closes its publisher/subscriber. Closing the BullMQ worker closes its emitter; SIGTERM/SIGINT drain the worker and queue. This cleanup does not implement a comprehensive shutdown deadline policy.

Evidence is split deliberately: `security.unit.test.ts` checks pure validators, JWT binding and limiter boundaries; `gateway-runtime.unit.test.ts` uses real local Socket.IO and disposable Redis with mocked database ports, including outage/reconnect and client cleanup; `live-authorization.test.ts` requires a guarded disposable PostgreSQL database and verifies actual account/session changes and REST/socket behavior. Native reconnection behavior and deployed multi-host networking require separate acceptance checks.
