# Verified uploads and storage cleanup — 22 September 2026

Implementation for [OVA-174](https://linear.app/ovalaydigital/issue/OVA-174) and the storage-deletion portion of [OVA-146](https://linear.app/ovalaydigital/issue/OVA-146). The validation section below records the original local checks; the [later deployment record](deployment-uploads-2026-09-22.md) contains TEST/staging rollout and real R2 evidence. Native interaction remains unverified.

## Upload contract

1. The mobile app reads the selected file once, rejects empty files and photos/documents over 10 MiB, and requests an upload with the exact byte size. A two-minute deadline covers reading, signing, PUT and finalization; a failed stage never returns an unverified key. Voice API uploads have a 20 MiB limit; the mobile voice feature remains unimplemented.
2. The API records the owner, purpose, scope, expected type/size and expiry before signing a five-minute PUT URL for `staging/<final-key>`. It also records delayed cleanup, including when the client never uploads anything.
3. `/api/me/uploads/finalize` checks ownership, object existence, exact size, MIME metadata and the first 512 bytes for a matching format signature. A conditional copy using the inspected ETag saves to the final key. That key is never exposed for PUT. Reusing the temporary PUT URL cannot replace already finalized content.
4. Attachment consumes the verified upload in the same transaction as the profile/verification/message reference. A file belongs to one owner, one purpose, one scope, and one reference. Repeating the same avatar, portfolio addition, document submission or stable-ID chat send is idempotent. Reusing a file for a different purpose/reference is rejected.
5. Unconsumed files expire after 24 hours. Expired and deleted final keys cannot be reattached. Existing saved legacy objects remain readable; newly submitted references must follow finalization when storage is enabled. The legacy storage-disabled profile URL mode remains for development.

Signature screening is not a malware scan or full media decode. PDF is allowed only for an ID document and copied with attachment disposition. The shared storage adapter signs content type and content length, suppresses automatic empty-body checksums when presigning, and bounds inspection/copy/deletion requests with deadlines.

## Durable cleanup

`StorageDeletion` is committed before references are cleared, inside the same transaction. The `storageCleanup` worker runs every five minutes and takes up to 100 due intents. Failures retain an attempt count, a sanitized reason and exponential backoff (up to 24 hours). Completed tombstones remain to block resurrection. A crash after provider success can repeat an idempotent delete.

Cleanup checks avatar, portfolio, verification/government-photo and message references while holding the same object lock used by attachment/finalization. Remaining references defer deletion. Historical chat keys must match the booking's actual participants and purpose before they enter cleanup. Profile/KYC legacy keys must match the owning usher's namespace. URLs and traversal-like values are never deletion targets. Retention deletes only the inventoried message IDs so a concurrent send cannot lose its reference without an intent.

Erasure inventories authored chat media and issued uploads before redaction, adds profile/KYC media, and retains cleanup work after account anonymization. Upload/attachment writers serialize with erasure on the owner. Erasure also clears business name, location/languages, profile display fields, raw government identity fields and notifications. The erasure response queues cleanup without waiting for provider calls (`objectsDeleted: 0`, `objectsPending` for queued final keys); the worker records confirmed successes and failed attempts separately; temporary keys retain their delayed cleanup schedule.

This is **not the complete OVA-146 inventory**: the retained checkout-email fingerprint in financial idempotency envelopes still needs a versioned privacy-preserving migration that preserves financial replay protection. Do not delete those records blindly. OVA-162's retention eligibility/fresh-message/open-dispute policy work also remains; this change preserves the existing eligibility windows.

## R2 rollout

- Apply the tracked `upload_intents_and_storage_deletions` migration before the API and worker. Distribute the updated mobile build with the new byte-size/finalization contract. Older app builds cannot create new attachments against this API contract; coordinate the release rather than permitting unverified fallback writes.
- Configure the existing `STORAGE_ENDPOINT`, `STORAGE_REGION=auto`, `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY`, and `STORAGE_SECRET_KEY` on both API and worker. Keep the bucket private; use signed reads. Do not place account credentials in the mobile app.
- Add a bucket lifecycle rule deleting only the physical temporary-object prefix after one day as a safety net for abandoned or late PUTs. With an account-root endpoint this is `staging/`; the existing bucket-path endpoint stores these under `<bucket>/staging/`. Inspect the physical prefix before configuring a rule. Never apply it to final `photos/`, `verifications/`, or `chat/` keys. This rollout does not change bucket lifecycle settings.
- Browser uploads require bucket CORS for the actual application origin, PUT/GET/HEAD, and the content-type header. Native uploads are not subject to browser CORS.
- Validate a real-device photo/ID upload, finalization, signed read, replacement, and failed-delete retry with a dedicated R2 test object before rollout. The local tests use a fake object store and a loopback S3 HTTP adapter.

The provider operations used are documented in Cloudflare's [S3 compatibility table](https://developers.cloudflare.com/r2/api/s3/api/) and [presigned URL guide](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), including conditional copy by source ETag. R2 fits the current S3 adapter; adopting it does not require a separate upload framework.

## Validation

- API/mobile typechecks, API test typecheck, package lint, affected test lint and whitespace checks pass.
- 24 distinct database cases pass: the final run passed all 8 upload tests and 10 attachment tests; the preceding run also passed all 6 chat history/retry/concurrency cases. Both disposable test schemas were removed after validation.
- 27 local cases pass: 12 format-signature cases, 2 S3 adapter/deadline cases, 8 scheduler/Redis lifecycle cases, and 5 mobile upload transfer cases. The initial loopback run was blocked by sandbox networking; the approved local-server rerun passed.
- The migration deploys without drift in a fresh isolated schema. All six temporary schemas used during migration authoring were removed.
- At the original local validation checkpoint, documentation checks passed (287 local links); no live R2 provider test, native interaction test, deployment or application-database migration had been performed. Later rollout evidence is recorded separately.

Sanitized database/adapter logs are retained locally under `documentation/validation-evidence/2026-09-22/uploads/`.

Migration authoring first ran `pnpm db:migrate --create-only` against disposable main/shadow schemas. Prisma reported unrelated schema-name drift in its shadow comparison. The fallback used Prisma's migration diff against the disposable main schema and accepted only the two additive tables and their indexes. A fresh isolated migration deployment and drift check then passed. No configured application schema was reset; the subsequent authorized deployment applies the additive migration to TEST/staging.

The real R2 round-trip exposed an existing bucket-path endpoint convention: physical object keys include the bucket prefix. The adapter now uses that same address for conditional copy, preserving existing objects. Three endpoint/path regression cases pass, and real R2 PUT, inspection, ETag-conditioned copy, signed download, unsigned S3 access denial and deletion were verified using dedicated temporary test objects. Their removal was confirmed. This does not audit public bucket domains or replace device validation.
