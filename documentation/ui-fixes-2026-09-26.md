# Mobile experience fixes — 26 September 2026

Implemented the actionable defects from the [deeper review](ui-deep-review-2026-09-26.md) and [initial review](ui-improvement-review-2026-09-26.md), preserving the approved layout, palette, typography and design-system components. No API, database, ledger or settlement-policy changes were required.

## Changes

| Area | Result |
|---|---|
| Checkout recovery | Pending bookings pass their existing order ID. The summary loads that order from the server and fetches every booked person; it does not depend on an intent stored on the original phone. Resume uses the existing order endpoint. |
| Payment summary | Missing people, a mismatched order/event, duplicate booking IDs, or a total that differs from the roster prevents a complete-looking payment summary. The error offers retry and access to payment status. Orders that are no longer payable offer View payment status. |
| Saved receipt cleanup | Completing server-order recovery also refreshes and acknowledges a matching local saved order, preserving unrelated saved intents. |
| Staff selection | Failed event or saved-checkout dependencies produce explicit retry screens. Existing selections remain in component state instead of being replaced by invented zero prices/capacity. |
| Withdrawals | Initial amounts and Withdraw all preserve fractional naira. Decimal entry converts to integer kobo without silently rounding extra decimal places. |
| Bank accounts | Add another account remains available after the first account is saved. The existing form can be cancelled back to saved accounts; the newly saved account becomes selected. Available bank names replace bare codes in selection and review. |
| Payout explanation | Applications, payment summary, check-in and wallet use shared wording for the approved holding period. Attendance, completion, wallet release and bank withdrawal remain distinct. |
| Profile setup | One submission lock spans save and refresh. Failed refresh preserves entered fields and explains that the save succeeded. Retrying unchanged fields refreshes without saving twice. Required inputs, limits and inline experience validation are visible. |
| Verification approval | Approval retries synchronize the authenticated account as well as checking verification. The screen distinguishes Identity approved from ready to apply. |
| Verification actions | Unverified job viewers can open verification/status from the primary action; applying remains gated. NIN/BVN choices expose their selected radio state. |
| Jobs | Booking badges use actual lifecycle states rather than treating every non-pending booking as success. Bookmark actions have per-job pending locks and success/failure feedback, plus recovery when saved jobs cannot load. |
| Discovery | Rating chips reflect the selected minimum. Filter counts include the search text and do not turn request failures into zero results. Empty searches offer relevant clear/reset actions. |
| Action labels | The event action that opens the conversation list is now Messages. |

The prior design-token and shared-component polish remains in place. This pass reuses those tokens rather than introducing a second visual system.

## Validation

- Mobile tests: **33 passing**, including 21 amount-entry cases and 10 order-recovery cases.
- Existing checkout and withdrawal controller regressions: **31 passing**. These exercise preserved intents, retries, duplicate submissions and withdrawal outcomes without live payments.
- Mobile TypeScript and lint checks passed during implementation. Lint retains two existing filesystem warnings in `plugins/with-smileid-host-sentry.js`; changed application code introduced no remaining lint findings.
- Android and iOS Hermes bundle exports passed. These validate bundling; they are not newly signed APK/IPA releases or physical-device acceptance tests.

Interactive checks used the real Profile Setup and Awaiting Approval components with simulated responses in a local React Native Web fixture. They made no server writes:

| Scenario | Observed result |
|---|---|
| Profile save succeeds, account refresh returns null | Form remains filled, Continue becomes available again, and a message explains the saved profile needs a refresh retry. No navigation occurs. |
| Retry the same profile after restoring the connection | Navigation proceeds to identity verification; the fixture recorded two refresh attempts and only one save. |
| Verification is approved but account synchronization fails | The screen explains the account update failure and offers status retry; its primary action permits browsing rather than claiming applying is ready. |
| Retry verification with successful account synchronization | The account refresh runs again, the error clears, You’re verified and Start applying appear, and the action navigates to Jobs. |

No warnings or errors were captured in the fixture browser console. Payment and withdrawal behavior was validated with source-backed regression tests, not real financial transactions. Native camera verification, VoiceOver/TalkBack announcements and full physical-device journeys still require device testing in a new app build.

Optional product extensions from the review—such as dedicated wallet booking-category filters or predicted release dates—were not introduced. Existing server-provided dates and financial rules remain authoritative.
