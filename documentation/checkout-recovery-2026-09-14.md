# Checkout recovery and reservation expiry — OVA-135

Each confirmation creates an Order, its pending bookings, a deterministic charge reference, and a Checkout checkpoint in one transaction. Caller/request idempotency still identifies the original order. Before initialization, the server commits INITIALIZING and attemptedAt; only that claim can dispatch initialization. It stores the returned HTTPS URL before returning READY. Remounting or retrying resumes that URL and order. Missing or uncertain initialization responses retain REVIEW and never trigger a new initialization or reference.

The mobile app persists caller/event-specific input and idempotency key before sending. It retains the server receipt until explicit terminal acknowledgment. Browser cancellation does not clear it. A manifest publishes immutable small SecureStore chunks atomically; incomplete storage blocks dispatch. UI effects are fenced across caller/event changes and unmount. Applications exposes saved checkout recovery without trying to accept already-booked staff again.

Reservations have a 30-minute review deadline. Under event → order → sorted booking locks, only a never-dispatched CREATED checkpoint or matching verified abandoned/failed evidence can expire a reservation. Expiry cancels pending bookings and refreshes staffing, without moving money. Network failure, missing references, unsupported verification, pending/ongoing/processing/queued/reversed, and unfamiliar statuses retain reservation and REVIEW. A five-minute job continues reconciling those references and conservatively backfills legacy pending orders.

A successful charge that wins the lock before expiry confirms the reserved bookings. A successful charge after EXPIRED records conserved HOLD liabilities against cancelled allocations, keeps those bookings cancelled, and atomically creates durable per-booking refund intents. Existing refund recovery completes them. Replacement bookings never lose their slots. Pending/completed refunds create one durable inbox notice per state for an active owner, linking directly to owner-authorized order status even after the original local receipt was acknowledged. Erased clients receive no new notices, while financial recovery remains possible.

Checkout email and hosted URLs are scrubbed on erasure. User locks prevent an in-flight initialization response from restoring erased fields. Legacy backfill for erased owners retains financial identity with blank email and no URL.

Paystack documents authorization URL/access code in the initialization response and using the retained access code to resume checkout. Its verification documentation distinguishes abandoned, failed, pending and other outcomes. The documented verify response does not provide recovery of a lost authorization URL; that case intentionally stays REVIEW instead of pretending it is READY. Sources: [Transaction API](https://paystack.com/docs/api/transaction/), [Accept payments](https://paystack.com/docs/payments/accept-payments/), [Verify payments](https://paystack.com/docs/payments/verify-payments/).

Validation is local: mocked HTTP contracts, pure mobile controllers/storage, static checks, and orchestrator-owned isolated database tests. No live Paystack account behavior, native browser/device interaction, deployment, or production migration execution is certified by this implementation. Migration SQL is tracked; the orchestrator applies it only to disposable validation storage.
